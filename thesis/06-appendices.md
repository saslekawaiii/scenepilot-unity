Полная редакция технического задания поставляется отдельным документом «Техническое задание WorldWeaver». Приложение фиксирует связь обязательных требований с реализацией. Приёмка выполняется по согласованным критериям и сохранённым протоколам.

# ПРИЛОЖЕНИЕ Г Порядок установки и повторения проверки

## Установка 1.1 и начало работы

Для редакторского чата используется Unity 6000.3.27f1. Можно открыть поставленный UnityProject с локальной file-зависимостью либо установить пакет в отдельный совместимый проект через Package Manager → Install package from tarball, выбрав com.worldweaver.toolkit-1.1.0.tgz. Зависимость Newtonsoft JSON 3.2.1 должна разрешиться через UPM. Для Git-установки используется URL репозитория с path=/Packages/com.worldweaver.toolkit и зафиксированным SHA редакции 1.1. Доступ к закрытому репозиторию предоставляет локальная авторизация Git; credentials в URL не включаются. Проверка чистого импорта 1.0 относится к исходной версии и сама по себе не подтверждает установку 1.1.

Локальный daemon Ollama должен быть доступен по http://127.0.0.1:11434. Начальное назначение чата — qwen3.5:9b; для retrieval NPC требуется embeddinggemma. Исторические qwen3.5:2b и qwen2.5-coder:latest сохраняются для повторения базовых исследований и runtime-сценариев. Модель 9B занимает значительную часть доступных 16 ГБ; выполнение в режиме «Баланс» с проверкой результата может занимать несколько минут. Веса не входят в поставку исходников; имена тегов и фактические digests записываются перед повторением. Изменение embedding-модели требует перестроения индекса знаний.

Основной путь — Tools → WorldWeaver → Чат. В одной беседе выбираются модель и режим, вводится описание мира, затем уточняются его параметры и создаётся NPC. Меню «+» подготавливает обычный запрос или прикрепляет сведения о выделении. История хранится в UserSettings проекта. Advanced Inspector с WORLD/NPC/KNOWLEDGE/MODELS/DEBUG используется для детального контроля и повторения прежнего процесса. Создание Demo in New Scene является отдельной командой демонстрации ядра; для обычного нового мира чат изменяет активную сцену и не очищает её.

При наличии бюджета после исполнения инструментов модель получает актуальное состояние для проверки исходного задания. Ответ complete:true с непустым actions остаётся намерением; результат следует сверять с Terrain, компонентами и параметрами. Если бюджет закончился после пакета, «Шаг выполнен» не обозначает завершённую дополнительную проверку моделью. Остановка сохраняет уже выполненные шаги. Стандартный Undo сцены и возврат C# являются разными действиями. Во время запроса текущий этап сопровождается прошедшим временем; этот таймер не является прогнозом оставшейся длительности.

## Программные проверки и семь запросов агента

Сначала выполняются EditMode и детерминированные PlayMode-проверки. В Test Runner следует выбрать соответствующие сборки и сохранить XML. Скрипт run_unity.py edit запускает EditMode, а play использует фильтр NavigationTests и AssistantBehaviorTests для обеих групп детерминированных проверок версии 1.1. Проверки с подставленным ILLMProvider не требуют настоящей модели и не считаются измерением её успешности. Последний подтверждённый EditMode на 60192a9 содержит 108/108; сохранённый PlayMode 3/3 выполнен на 0aa9bdf. При повторении эти версии и даты записываются отдельно. До batch-запуска закрывается другая копия Editor с тем же projectPath.

Семь запросов ChatAcceptanceRunner выполняются в одном новом чате: создание долины 160×160 с 12 деревьями, 3 домами и 4 камнями; изменение прежнего height до 24; создание Игната со знанием о воротах; изменение его цели; создание ровно трёх оранжевых Point Light; подготовка C# для вращения по Y без импорта; объяснение выбранной модели и фактического состава сцены без мутации. Точные формулировки находятся в исходнике runner и записываются в JSON вместе с ответами. В версии критериев 2 новые Point дополнительно проверяются внутри границ Terrain, не менее чем на 3 м над поверхностью и сгенерированной водой; их range должен достигать земли. Исходный протокол с узким подсчётом света не заменяет этот повтор.

Явная команда Tools → WorldWeaver → Testing → Chat Acceptance создаёт пустую тестовую сцену. В GUI перед этим предлагается сохранить текущую сцену. Для воспроизведения следует использовать выделенный тестовый проект, а не рабочую сцену потребительского проекта. Обычные инструменты чата не создают и не очищают сцену; создание отдельной сцены относится только к запущенному испытанию.

Для batch-запуска WW_UNITY задаёт абсолютный путь к Unity, WW_PROJECT — к тестовому проекту, WW_AGENT_REPORT — новый абсолютный путь JSON. Эти значения выбираются до команды; опубликованный файл не перезаписывается. Пример запуска из каталога проекта:

```sh
WW_CHAT_MODEL=ollama:qwen3.5:9b \
WW_CHAT_OUTPUT="$WW_AGENT_REPORT" \
"$WW_UNITY" -batchmode -nographics \
  -projectPath "$WW_PROJECT" \
  -executeMethod \
  WorldWeaver.Editor.Assistant.ChatAcceptanceRunner.Run
```

Флаг -quit не добавляется: асинхронный runner завершает batch-процесс после записи результата. В JSON сохраняются выбранная модель, условия запуска, prompt, попытки с запросом и схемой, результаты инструментов, состояние до и после, время и причины неуспеха. Нужно проверить completed, passed, success и причины каждого запроса, а также файлы истории по historyFolder. Для каждой попытки сопоставляются RawResponse, NormalizedResponse, RepairKind и Accepted: узкая нормализация Classic может сохранить исходный повреждённый ответ и отдельный принятый вариант. Это не ручная замена команд; локальный Ollama этот адаптер не использует. Прерванная серия и невыполненные зависимые задания не объявляются успешными. Один последовательный разговор не оценивает общую вероятность выполнения произвольной задачи. Сохранённые local9b-v2 7/7 и его отдельный кодовый прогон 11/11 относятся к 0aa9bdf; они не считаются новым повторением на 60192a9.

Ожидаемый исход шестого запроса — draft_script, сохранённый для просмотра. ChatAcceptanceRunner не нажимает «Применить» и не импортирует C#. Седьмой запрос должен сохранить этот план и не менять сцену. Выполнение этих условий проверяется независимо от правильности самого текста программы. Формальный проход draft/review-gate не означает допустимость Unity API или правильную зависимость скорости от Time.deltaTime; эти свойства проверяются по точному исходнику до импорта.

## Просмотр C# и отдельная проверка компиляции

В пользовательском процессе исходник читается в сообщении чата и импортируется явной кнопкой применения. Затем проверяются реальные сообщения Unity compiler. После успешной компиляции подключение компонента выполняется отдельным просмотренным планом. В сообщении доступного сохранённого импорта кнопка «Вернуть предыдущий код» восстанавливает прежний файл или удаляет новый и инициирует повторную компиляцию. Последующие ручные правки не перезаписываются. Возврат исходника не заменяет Undo других изменений сцены. После применения и возврата в сообщении остаётся снимок принятого исходника для чтения и копирования; он не обязан совпадать с текущим файлом. Для повторного импорта нужен новый действующий PendingPlan, а не нажатие на исторический снимок.

Для воспроизводимого испытания предусмотрен ChatCodeAcceptanceRunner. Он использует уже подготовленный pending-план из сохранённой изолированной истории этого же проекта, а не запрашивает новую программу у модели. До запуска необходимо содержательно проверить точный args.code и записать SHA-256 его UTF-8-строки. Контрольная сумма файла с добавленным служебным маркером или изменёнными переводами строк не заменяет hash исходной строки. Входной JSON должен сохранять sessionId, historyFolder и неизменённый capturedReviewOnlyPlans; одного перенесённого JSON без истории недостаточно.

Для испытания требуется новое уникальное имя C#-класса и файла. Runner исполняется в выделенном batch-проекте, проверяет отсутствие текущей компиляции и не применяет код, если сохранённый backup занят другим импортом. При несоответствии проверенного hash автоматического применения не происходит. WW_REVIEW_HASH задаётся только после просмотра конкретного исходника, WW_CODE_REPORT — новым путём протокола. Команда выполняется из WW_PROJECT без -quit:

```sh
WW_CHAT_INPUT="$WW_AGENT_REPORT" \
WW_CODE_REVIEW_SHA256="$WW_REVIEW_HASH" \
WW_CODE_OUTPUT="$WW_CODE_REPORT" \
"$WW_UNITY" -batchmode -nographics \
  -projectPath "$WW_PROJECT" \
  -executeMethod \
  WorldWeaver.Editor.Assistant.ChatCodeAcceptanceRunner.RunCLI
```

Проверка охватывает чтение импортированного файла, события настоящей компиляции, полученный тип MonoBehaviour, действительное подключение к собственной тестовой фигуре, восстановление исходного файлового состояния, повторную компиляцию и очистку временной сцены. По выходу изучаются checks, errors, sourceRestoredAtExit, manualCleanupRequired и manualCleanupPaths. Компиляция и наличие компонента не подтверждают его поведение в Play Mode: например, вращение надо наблюдать отдельно. Принятый C# выполняется с правами Unity; hash, просмотр и компилятор не создают sandbox.

## Повторение исходного QA-эксперимента 1.0

Отдельная копия репозитория на теге experiment-2026-10-30 используется для воспроизведения базового QA. Его корпус содержит 30 вопросов для каждой из трёх конфигураций: локальная Qwen3.5 2B без RAG, та же модель с RAG и облачная GPT-OSS 20B с RAG. Всего сохранены 90 обращений: 89 текстовых ответов и один HTTP 400. Эти наблюдения относятся к исходному контракту и не пересчитываются как ответы редакторского агента 1.1.

ResearchRunner запускается с WW_EVAL_PROVIDER=local либо cloud. Вопросы читаются из scenarios.json; для local выполняются конфигурации без RAG и с RAG, для cloud — с RAG. Накопление памяти выключается. До нового запуска исходные JSONL архивируются или для эксперимента используется отдельная копия: повторное выполнение перезаписывает соответствующие данные.

Для исходной бесплатной конфигурации CloudRoutes оставляет Terrain и Planning локальными, а Dialogue использует Pollinations Classic и openai-fast. В trace проверяется фактическая модель. На исходном теге установлен интервал обращений 31 секунда; он сохраняется как исторический параметр опыта. В текущей редакции от 31.10.2026 подтверждён серверный бесплатный интервал 45 секунд, клиент использует запас до 46 секунд и предел max_tokens=1500. Перенос новой квоты в старый протокол был бы изменением условий, поэтому повторный inference оформляется отдельно. Текущая доступность стороннего сервиса проверяется заново; одинаковые параметры прошлого API не обещают идентичный ответ.

Скрипт analyze_results.py читает сохранённые JSONL и terrain.json и записывает metrics-per-question.csv, summary.json и графики. Повторение агрегатов требует Python с matplotlib и numpy, но не запуска модели. Сначала сохраняются прежние аналитические артефакты; новый анализ не должен незаметно заменить опубликованный протокол. Совпадение факта в сырой речи и факт в принятом игроком ответе учитываются раздельно.

Исходные сквозные runtime-сценарии запускаются отдельно с WW_REAL_TESTS=1 и фильтром RealProviderIntegration. Без флага они пропускаются; это не подтверждает доступность inference. Движение проверяется по NavMeshAgent и изменению позиции в подготовленной области, передача — по обоим Inventory. При отказе локального соединения проверяются daemon, модели и embedding endpoint. Исторический транспорт учитывал HTTP 429 и 402 с Retry-After. В текущем адаптере среди HTTP 402 ограниченно повторяется только распознанный FREE_LIMIT; обычная платёжная ошибка не запускает повтор или оплату. HTTP 400 и ошибочный JSON не превращаются в действие вручную.
