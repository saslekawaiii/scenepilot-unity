# ПРИЛОЖЕНИЕ А Техническое задание

Полная редакция технического задания поставляется отдельным документом «Техническое задание WorldWeaver». Приложение фиксирует связь обязательных требований с реализацией. Приёмка выполняется по согласованным критериям и сохранённым протоколам.

| Требование | Основные элементы реализации | Доказательство |
|---|---|---|
| Terrain по описанию | TerrainSpec, TerrainGenerator, TerrainAuthoring | Тесты разбора, диапазонов и seed |
| Модельные маршруты | ModelRouter, OrchestratorProfile | Тест назначения разных задач |
| Локальный inference | LocalProvider, Ollama | Real-provider JSON и PlayMode |
| Бесплатный cloud | OpenAICompatibleProvider, Pollinations | HTTP-проба и 30 QA-вызовов |
| Индивидуальный RAG | RagIndex, InMemoryVectorStore | Scope-тест и hit@3 |
| Проверка действий | NpcDecision, ActionDispatcher | Amount, target, permissions и double spend |
| Перемещение | WorldAction, NavMeshAgent | PlayMode MoveTo/Follow |
| Диагностика | PipelineTrace, WorldWeaverWindow | Trace JSON и вкладка Debug |

Исходный набор QA-сценариев содержит 30 строк в results/scenarios.json. В каждом случае зафиксированы вопрос, ожидаемые варианты и source ID. Файл metrics-per-question.csv связывает эти сценарии с наблюдавшимся ответом и агрегатами. При повторном испытании требуется сохранить версии моделей и условия запуска, а не сравнивать только итоговые проценты.

Дополнительная activity-диаграмма показывает обработку ошибки и успешного ответа. Это схема реализованного pipeline, а не обещание автоматического исправления любого ответа модели.

# ПРИЛОЖЕНИЕ Г Порядок установки и повторения проверки

Для быстрого старта устанавливается Unity 6000.3.27f1 и открывается проект UnityProject. Пакет находится отдельно в Packages/com.worldweaver.toolkit и подключён через локальную file-зависимость. Для установки в другой проект выбирается Window → Package Manager → Add package from tarball и передаётся com.worldweaver.toolkit-1.0.0.tgz. Новый проект должен получить зависимость Newtonsoft JSON 3.2.1. Проверка такого импорта с новой Library сохранена в clean-install.json.

После импорта через Tools → WorldWeaver → Create Demo in New Scene создаётся демонстрация. Она содержит собственные TerrainData, материалы, профили моделей и KnowledgeBase. Повторное создание формирует новые ассеты с уникальными именами, поэтому перед ним следует сохранить текущую сцену. Пример не требует удаления прежних Terrain другого проекта.

Локальный daemon Ollama должен быть доступен по http://127.0.0.1:11434. Для маршрута Terrain необходим qwen3.5:2b, для Dialogue и Planning — qwen2.5-coder:latest, для индексации — embeddinggemma. Имена тегов следует сопоставить с локальным каталогом. Изменение embedding-модели требует перестроения индекса. Внешние модельные веса в поставку исходного кода не включаются.

Для бесплатного диалога выбирается CloudRoutes: Terrain и Planning остаются локальными, Dialogue использует Pollinations Classic и псевдоним openai-fast. В debug проверяется фактическое model из CompletionResult. Одновременно выполнять несколько cloud-сценариев с одного IP не рекомендуется из-за общей квоты. Ключи и платёжные данные для проверенной конфигурации не нужны.

Первый этап повторной проверки включает EditMode и детерминированный PlayMode. Реальные провайдеры проверяются отдельно с флагом WW_REAL_TESTS=1 и фильтром WorldWeaver.Tests.RealProviderIntegration. Без флага эти тесты пропускаются, поэтому обычный успешный набор без внешней модели нельзя выдавать за подтверждение inference. Перед запуском необходимо завершить другую копию Editor, использующую тот же projectPath.

Для повторения QA применяется ResearchRunner с WW_EVAL_PROVIDER=local либо cloud. Вопросы читаются из scenarios.json; для local выполняются конфигурации без RAG и с RAG, для cloud — с RAG. Накопление памяти выключается. Полученные JSONL следует сохранить в новый каталог или зафиксировать отдельной версией, чтобы исходные результаты не были потеряны.

Скрипт analyze_results.py получает сохранённые JSONL и terrain.json и записывает metrics-per-question.csv, summary.json и графики. Воспроизведение агрегатов требует Python с matplotlib и numpy; оно не требует повторной оплаты API или запуска модели. Для проверки конечного игрового эффекта используются XML и end-to-end JSON, содержащие остатки Inventory и измеренное изменение позиции.

При отказе локального соединения сначала проверяются daemon и наличие модели, затем доступность embedding endpoint. При HTTP 429 либо 402 с Retry-After следует дождаться разрешённого интервала; при HTTP 400 исправляется запрос, поскольку автоматический повтор такого тела обычно бессмысленен. Ошибочный JSON анализируется в Debug и не превращается в действие вручную. При отклонённом MoveTo проверяются положение агента на NavMesh и достижимость целевой точки.
