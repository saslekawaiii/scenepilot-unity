# ПРИЛОЖЕНИЕ Б Материалы повторения проверки

## Б.1 Установка и паспорт опыта

Используется отдельный Unity-проект, соответствующий версии проверяемого пакета. Для R3 проверен архив com.worldweaver.toolkit-1.2.0.tgz; его SHA и результат нового проекта сохранены в clean-install-1.2.0.json. До запуска фиксируются Unity patch, ОС, оборудование, Git SHA, версия tarball, модель и её digest, endpoint и параметры inference. Архивы прежних редакций не подменяются новой сборкой. Проверка начинается с новой Library, чтобы исключить зависимость от локального кэша разработчика.

Для готового игрока выбирается legacy Input Manager или Both. Сохранённый проект испытан с activeInputHandler = 0; режим только New Input System требует дополнительного подключения ввода. До мутационной задачи также проверяются пределы checkpoint: до 20000 файлов и 300 МиБ, 1–8 загруженных сцен, без baked lighting.

После добавления пакета открывается основной чат WorldWeaver. Выбираются доступная модель и режим. Для локального варианта предварительно запускается Ollama и проверяется загрузка нужных моделей. Внешний API используется только при фактической бесплатной доступности без покупки токенов. Если сервис недоступен, сохраняется исход ошибки; скрытая подмена модельного ответа запрещена.

Для своего сервера нажимается «Добавить API…». Указываются протокол Ollama либо OpenAICompatible, URL и точный ID модели. Пример локального OpenAI-compatible пути — http://127.0.0.1:11434/v1; авторизация для такого сервера не обязательна. Для внешнего сервера выбирается поддерживаемый им формат JsonSchema, JsonObject либо Text. В поле «Имя переменной» вводится имя заранее заданной переменной окружения, а не значение ключа. Для ключа только на время работы Unity используется отдельное поле «Ключ API»; эти два способа не заполняются одновременно.

После «Добавить и выбрать модель» выполняется «Проверить соединение». Получение списка не запускает inference. Команда «Проверить ответ» используется отдельно и только при допустимости расхода квоты. Отсутствие /models у нестандартного сервера не доказывает отсутствия Chat Completions, поэтому исход проверки и выбранный протокол фиксируются в паспорте опыта. Поддержка собственного API не означает универсальной совместимости со всеми поставщиками.

Перед мутацией сохраняется исходная сцена. Для нового опыта создаётся отдельная тестовая сцена или точный снимок исходного состояния. Нельзя запускать runner, рассчитанный на пустую сцену, поверх несохранённой пользовательской работы. Пути проверяемых ассетов фиксируются до и после, а число ручных действий записывается отдельно от модельного исполнения.

## Б.2 Программные и предметные проверки

Программные тесты запускаются средствами Unity Test Framework. В сохранённом скрипте run_unity.py режим edit выбирает EditMode, а play — прежние NavigationTests и AssistantBehaviorTests. Полная проверка 1.2 дополнительно включает WorldGameplayTests и WorldScheduleTests: именно четыре fixture перечислены в integration-1.2-seventh-r3-summary.json. Для повторения полного PlayMode-набора выбирается соответствующий фильтр Unity Test Runner; запуск старого сокращённого фильтра не считается повторением девяти проверок. XML сохраняется до следующего прогона. Наличие успешного XML не означает выполнения всех модельных запросов.

Для редакторского сценария сохраняются исходный prompt, попытки, принятые планы и read-back. Независимая проверка читает компоненты и файлы, не полагаясь на Summary инструмента. Если задания выполняются последовательно в одной беседе, этот факт указывается: позднее задание зависит от ранее созданного состояния.

Проверка мира включает TerrainSpec, размеры, seed и логические объекты. Проверка света включает тип, цвет, интенсивность, range, положение над поверхностью и принадлежность точки Terrain. Для NPC проверяются настоящие поля личности, KnowledgeBase, scope и маршруты. Наличие компонента patrol не считается доказательством полного прохождения пути.

Для игрового действия сравниваются оба инвентаря до и после. Для движения фиксируются начальная позиция, путь и конечная область. Для нового Save/Load проверяется дисковый файл и восстановленные данные после пересоздания состояния. Повторное завершение доставки проверяется отдельно, чтобы обнаружить дублирование награды.

## Б.3 Просмотр и компиляция исходника

Модельный draft сохраняется без автоматического импорта. Проверяется точный текст, путь и SHA-256. Вращающий пример должен использовать существующий overload Unity API, правильную ось, единицу угловой скорости и умножение на Time.deltaTime при покадровом обновлении. Статическая компиляция с Unity reference assemblies является предварительным этапом, а не подтверждением исполнения в Unity.

После просмотра запускается отдельный реальный импорт. Запись, событие компилятора, тип компонента и attach проверяются раздельно. Во время reload состояние ожидания сохраняется. После возврата проверяются исходный файл, .meta, отсутствие лишнего компонента и результат повторной компиляции.

Двухимпортный сценарий использует заранее просмотренные версии A и B. Сначала импортируется A, затем B в тот же путь. Попытка вернуть A поверх B должна быть отклонена. Затем возвращаются B и A, проверяются обе резервные версии. Дополнительно вносится контролируемая ручная правка, после которой автоматическое восстановление обязано отказаться от перезаписи.

## Б.4 Исторический корпус индивидуальных знаний

Исходный QA-эксперимент относится к тегу experiment-2026-10-30. Он содержит три группы по 30 запросов без накопления памяти: local-no-rag, local-rag и cloud-rag. Для каждой строки сохраняются ожидаемые варианты ответа, правильный DocumentId, raw trace, принятый результат и время. Неуспешный запрос не удаляется из знаменателя.

Скрипт analyze_results.py агрегирует сохранённые JSONL. Совпадение факта в исходной речи, факт в принятой реплике, JSON-valid, принятие действий и retrieval считаются раздельно. Повтор анализа над теми же строками должен воспроизводить сводку. Повторный inference представляет новый опыт и может дать другой результат.

Содержание корпуса хранится в электронных материалах. Оно является авторским лором вымышленного мира и не предназначено для проверки общих энциклопедических знаний модели. При расширении исследования подготавливается новый независимый набор, включая неизвестные факты, противоречивые документы и отрицательные запросы доступа.

## Б.5 Ранние отрицательные наблюдения 1.2

Первые два незавершённых модельных прогона 1.2 сохранены отдельно. В первом записаны три неуспешных задания с ожиданием около 150 с каждое; во втором — два с длительностью около 153 и 242 с. Оставшиеся случаи не завершены. Поздние запросы зависят от не созданного первым запросом состояния и не являются независимыми повторами. В третьей попытке Balanced один случай завершился лимитом через 240,128 с. При этом в сцене уже находились Terrain 160 × 160 м, 12 деревьев, 3 дома и 4 камня, а массив высот не был плоским. Создание мира состоялось, но завершающий проверочный ответ не уложился в бюджет. Изменение контекста и нагрузка машины различались; единственная причина задержки не установлена.

Последующая попытка Deep на пятом срезе завершила два первых задания с положительными предметными проверками: создание мира за 190,035 с и изменение высоты за 162,315 с. Затем разговор остановлен для исправления маршрутизации запроса о свете. Оставшиеся пять заданий не завершены. Это две успешные выполненные задачи незавершённой беседы, а не итог «2/7» или «7/7».

Полный разговор на шестом срезе завершил все семь заданий и прошёл пять автоматических условий. В четвёртом случае запрос изменения цели NPC прервался через 240,444 с, цель не изменилась. В пятом созданы три Point, но явный on_terrain:false оставил их под поверхностью; прежняя экранная проверка количества ошибочно сообщила положительный итог. При создании NPC также появилось незапрошенное покачивание. В последнем read-only случае сцена сохранилась, однако ответ содержал неподтверждённые заявления о доле воды и назначенных маршрутах. Следовательно, 5/7 не означает пять полностью достоверных ответов.

Шестое условие этого разговора подтверждало только сохранение draft для просмотра. Исходник передавал Mathf.Deg2Rad × 30 в принимающий градусы Transform.Rotate. После просмотра точный неизменённый исходник импортирован в изолированном проекте; реальное Play-измерение дало 1,051° вместо ожидаемых 60,213° за 2,007 с, 99 отсчётов. Неподвижный контроль дал 0°. Протокол `rotation-runtime-1.2-sixth-fresh-draft.json` сохранил отрицательный исход и совпадение SHA до и после. Наличие draft и успешная компиляция не подтвердили требуемую угловую скорость.
