# 1 Введение

Наименование разработки — программный инструментарий WorldWeaver. Тема ВКР — «Разработка интеллектуального инструментария для автоматизированного создания динамических игровых миров». Область применения — учебные и экспериментальные проекты Unity, в которых требуется совместная подготовка окружения, неигровых персонажей, знаний и взаимодействий.

Инструментарий поставляется как UPM-пакет. Он включает редакторскую и исполняемую части. Основной пользователь — разработчик Unity-проекта. Создаваемая демонстрационная сцена является средством проверки пакета, а не самостоятельным коммерческим игровым продуктом.

# 2 Основания для разработки

Разработка выполняется в рамках выпускной квалификационной работы бакалавра по направлению 09.03.01 «Информатика и вычислительная техника», профиль «Разработка игровых и XR приложений», ВолгГТУ, ФЭВТ, кафедра САПР и ПК. Исполнитель — Коваленко Кирилл Дмитриевич, группа ИВТ-465.

Реквизиты приказа об утверждении темы, руководителя и календарного задания заполняются по официальным документам вуза. Состав документа основан на ГОСТ 19.201-78 [28].

# 3 Назначение разработки

Функциональное назначение — преобразование естественно-языковых запросов в проверяемые операции над игровым миром, создание NPC с индивидуальными знаниями и исполнение ограниченного набора игровых действий. Эксплуатационное назначение — работа в существующем Unity-проекте с возможностью замены модельного провайдера и повторного использования компонентов.

Результат должен оставаться доступным через обычные компоненты и ассеты Unity. Запрещено выдавать текстовое подтверждение модели за доказательство изменения сцены. Пользователь должен различать предложение, применённую операцию, результат компилятора и незавершённое условие.

## 4.2 Требования к надёжности

Ошибочный план должен отклоняться до изменений. При исполнительной ошибке восстанавливается группа Undo и удаляются только ассеты, созданные данным пакетом. Операции чтения не создают фиктивную отмену. Сохранение сцены выполняется только по явной команде.

До фиксации операция может быть отменена без побочного эффекта. После фиксации результат должен оставаться указанным, даже если отменена последующая индексация памяти. Статус отмены не должен провоцировать повтор уже состоявшейся передачи предмета.

При восстановлении исходника текущее содержимое должно совпадать с ожидаемой версией после импорта. При конфликте ручной правки требуется контролируемый отказ. Для перекрывающихся импортов сохраняются обе резервные версии и допустимый порядок возврата.

После reload система должна распознавать незавершённую компиляцию и не выдавать отсутствие события за успех. После загрузки сохранения награда не выдаётся повторно. Повреждённый файл не должен молча заменять пригодное состояние пустыми данными.

## 4.3 Условия эксплуатации и технические средства

Основная целевая среда — Unity 6000.3.27f1 или версия, отдельно подтверждённая установочным протоколом. Проверка ядра 1.0 на Unity 2022.3 не подтверждает полную совместимость новых функций. Требуются установленный пакет и доступный endpoint выбранного провайдера. Для локального режима требуется отдельный сервер Ollama с загруженными моделями.

Готовый клавиатурный игрок использует legacy Input Manager. Для демонстрации требуется этот режим либо Both; испытанный проект использует activeInputHandler = 0. Для проекта только с New Input System необходима отдельная интеграция ввода; такая конфигурация не считается проверенной.

Checkpoint мутационного обращения ограничен 20000 файлами, 300 МиБ включая рабочие состояния и 1–8 загруженными сценами. Резервируются Assets, ProjectSettings и манифесты пакетов; восстановление файлов ограничено изменённым множеством с контролем конфликтов. Сцены с baked lighting данным механизмом не поддерживаются. Эти пределы учитываются до начала задачи, а не скрываются общим обещанием совместимости с любым проектом.

Испытательная машина — Apple M4, 16 ГиБ памяти, macOS 15.7.4. Это паспорт проведённых измерений, а не доказанный минимальный аппаратный порог. Большие модельные запросы выполняются последовательно. Недостаток памяти и недоступность сервера отражаются как ошибки среды.

Работа с бесплатным внешним API не должна требовать пополнения баланса, оформления платной подписки или передачи ключа в исходники. Доступность и квота внешнего сервиса не гарантируются пакетом. Разрешён явный локальный режим.

## 4.4 Информационная и программная совместимость

Данные сцены представлены обычными компонентами и ScriptableObject. Текстовые знания поддерживают заявленные установленной версией форматы. Сериализуемые структуры имеют различимый формат версии. Смена embedding-модели требует совместимого индекса или переиндексации.

Endpoint удалённого сервера использует HTTPS; локальный HTTP ограничивается loopback. Credentials не помещаются в URL, пакет и исследовательские протоколы. Контекст ограничивается необходимыми данными, а scopes проверяются до retrieval.

В UserSettings сохраняются только несекретные сведения подключения и имя переменной окружения. Введённый ключ действует в процессе Unity и не записывается в файл или историю; для постоянного доступа используется внешняя переменная окружения. Проверка соединения должна читать список и свойства моделей без генерации; запрос проверки ответа выполняется отдельной явной командой. Форматы ответа выбираются по возможностям конкретного API. Нативные Anthropic Messages и Gemini в этот контракт не входят.

Новое C# не исполняется в sandbox. Просмотр, статическая проверка и компиляция имеют ограниченную область и не гарантируют безопасности. Для обычных операций используются встроенные инструменты с конечным набором параметров.

## 4.5 Требования к результату и ограничения

Процедурное окружение использует примитивы и собственные материалы; оно не объявляется генерацией художественных ассетов коммерческого уровня. Рельеф воспроизводим при одинаковых параметрах в проверенной среде. Межплатформенная битовая идентичность требует отдельного опыта.

Качество ответа, полнота задания и сохранность проекта оцениваются раздельно. Система не гарантирует отсутствие всех фактических ошибок модели. Текстовые ограничения характера NPC не считаются формально обеспеченными правилами, пока они не представлены детерминированной проверкой.

## 4.6 Маркировка и упаковка

Поставка электронная: архив UPM-пакета, исходники и документация. В package.json указываются имя и версия; для передаваемого архива сохраняется SHA-256. В упаковку не включаются credentials, служебные кэши и пользовательские сохранения. Физическая маркировка носителей не устанавливается.

## 4.7 Транспортирование и хранение

Передача выполняется копированием электронных файлов с проверкой контрольных сумм. Исходники и протоколы сохраняются с версиями. Резервные копии импортов отделяются от распространяемого пакета. Специальные климатические условия для программных файлов не устанавливаются; условия физического носителя определяются его изготовителем.

# 5 Требования к программной документации

Поставка должна содержать пояснительную записку, настоящее ТЗ, инструкции установки и повторения испытаний, описание интерфейсов расширения, перечень известных ограничений и машиночитаемые протоколы. Полное ТЗ включается в приложение пояснительной записки и отдельно формируется из одного исходного файла.

У каждой внешней зависимости указываются назначение и лицензия. Для включённых навыков сохраняются исходный репозиторий и pinned commit. Исходники продукта и исследования не содержат секретов и не требуют закрытого служебного каталога для воспроизведения документов.

# 6 Технико-экономические показатели

Требование оплаты API в приёмочных опытах — ноль. Локальное выполнение использует оборудование пользователя. Нулевая цена вызова не означает нулевую стоимость владения. Срок окупаемости, процент экономии труда и коммерческий эффект без измерений не устанавливаются.

Для оценки производительности фиксируются полное время задания, время провайдера и число исправлений. Время одной генерации массива не считается временем подготовки готового мира. Сопоставление с аналогом допускается только при одинаковых входах и разрешениях либо явно обозначается как анализ документации.

# 7 Стадии и этапы разработки

Последовательность работ: анализ задачи и аналогов; формирование требований; проектирование контрактов и границ; реализация основы и расширений; программные испытания; реальные модельные сценарии; независимая предметная проверка; чистая установка; подготовка документации. Календарные даты определяются утверждённым заданием на ВКР.

Каждый эксперимент имеет собственный checkpoint. Изменение кода после выявления дефекта требует нового прогона соответствующей проверки. Исторический неуспех сохраняется вместе с первоначальным критерием.
