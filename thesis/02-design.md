# 2 ПРОЕКТИРОВАНИЕ ИНСТРУМЕНТАРИЯ

## 2.1 Требования и границы системы

Исходное техническое задание определяет инструментарий как подключаемый продукт для Unity 6+, а не отдельную игру. Для реализации выбран UPM-пакет WorldWeaver с демонстрационным проектом. Пакет должен предоставлять авторинг в Editor и компоненты, которые продолжают выполнять свои функции в Play Mode.

Разработчик ставит задачу в редакторском чате, выбирает модель и предел глубины обработки, затем проверяет план и результаты изменений. Описание рельефа, личность NPC, документы знаний и разрешённые действия могут задаваться естественным языком с последующим переводом в проверяемые параметры. Игрок в Play Mode обращается к уже созданному персонажу и наблюдает речь и последствия его решения. Внешние системы предоставляют только inference: текстовый completion или embedding-вектор. Их вывод интерпретируется C#-слоем; непосредственного сетевого доступа к объектам Unity им не предоставляется.

Обязательные функции ограничены текстовым взаимодействием, редакторскими инструментами сцены, Terrain, retrieval, действиями NPC и диагностикой. Для небольших дополнительных компонентов предусмотрен отдельный просмотр C# и отчёт о компиляции. Голосовые интерфейсы и извлечение текста из PDF не включены в проверенный сценарий. Это ограничение не скрывается под общим утверждением о поддержке любых источников. Импорт знаний принимает TXT, Markdown и JSON с установленным форматом.

| Группа требований | Проектное решение | Способ проверки |
|---|---|---|
| Переносимость | Отдельный UPM-пакет, сборки Editor и Runtime | Установка и компиляция в тестовом проекте |
| Редакторский диалог | История, EditorPlan и ограниченный цикл инструментов | Несколько шагов с фактическим чтением результата |
| Сохранность сцены | Предконтроль плана, ownership, Undo и учёт новых ассетов | Отказ до записи и откат ошибочного пакета |
| Управляемость Terrain | TerrainSpec и детерминированный C# | Повторная генерация по seed и спецификации |
| Индивидуальные знания | Scope перед поиском | Тест исключения документа другого NPC |
| Управляемые последствия | NpcDecision и ActionDispatcher | Неверные amount, target и permissions |
| Несколько моделей | ModelTask и OrchestratorProfile | Проверка разных назначений маршрутов |
| Отказоустойчивость | Timeout, cancellation и bounded retry | Локальный HTTP-сервер ошибок |
| Диагностика | Результаты инструментов, PipelineTrace и Debug | Сопоставление плана, проверки и состояния Unity |
| Расширение C# | Просмотр исходника, импорт и события компилятора | Отдельный статус записи, компиляции и подключения |

Нефункциональные требования связаны с сохранностью сцены и контролем ресурсов. Редакторский исполнитель действует только в активной загруженной сцене и не создаёт новую сцену вместо неё. Новые объекты помещаются в собственную группу WorldWeaverGenerated и получают маркер GeneratedSceneObject. Само совпадение имени с этой группой не подтверждает владение. Изменение существующего объекта требует явной цели; удаление разрешено только для собственных объектов без посторонних потомков. Повторная генерация Terrain дополнительно использует GeneratedTerrain. Локальные модели хранятся вне репозитория, а количество октав, размер ответа, число фрагментов и создаваемых объектов имеют явные пределы.

## 2.2 Структура Unity Package

Пакет размещён в каталоге Packages/com.worldweaver.toolkit. Файл package.json определяет имя, версию и зависимость от официального пакета Newtonsoft JSON. Сборка WorldWeaver.Runtime содержит модели данных, providers, RAG, действия, компоненты NPC и Terrain. Сборка WorldWeaver.Editor содержит чат на UI Toolkit, контроллер сеанса, исполнитель инструментов, компоновщик окружения, расширенное окно настройки и средства исследования.

Разделение сборок не позволяет runtime-коду зависеть от UnityEditor. Это важно для дальнейшего использования игровых компонентов за пределами редактора. Средства измерений, создание ассетов и графический авторинг остаются в Editor. Тесты вынесены в отдельные сборки EditMode и PlayMode и подключаются через testables демонстрационного проекта.

Unity Package Manager поддерживает Git-зависимости и выбор подкаталога пакета через параметр path [2]. Такая структура позволяет держать программный продукт, демонстрацию и документы в одном репозитории, сохраняя независимую точку установки. Для локальной разработки используется относительная file-зависимость; она не должна ошибочно публиковаться как универсальный сетевой адрес.

Редакторский слой версии 1.1 разделён на представление WorldWeaverChatWindow, ChatController, SceneToolExecutor, WorldComposer, ChatHistoryStore и ScriptDrafts. Представление не исполняет команды самостоятельно. Контроллер управляет запросом и историей; исполнитель проверяет и применяет EditorPlan; компоновщик создаёт геометрию и ассеты; отдельный обработчик кода отслеживает компиляцию и восстановление файлов. Такое разделение позволяет подменять ILLMProvider в тестах без подмены реальных операций над сценой.

На рисунке показаны редакторский чат, контроллер, исполнитель инструментов, обработчик C# и компоненты генерации и runtime. Связи отражают разделение редакторского плана EditorPlan и игрового решения NpcDecision; подробный порядок раундов раскрывается далее в описании контрактов. Во время игры IntelligentNPC передаёт запрос в NpcPipeline, использующий retrieval, router и dispatcher независимо от конкретного поставщика inference.

## 2.3 Маршрутизация модельных задач

Редакторский агент использует выбранную для беседы модель. Настройка мощности изменяет бюджет обработки: число модельных раундов, лимит вывода, контекст и время ожидания. Режимы «Быстро», «Баланс» и «Глубоко» допускают соответственно один, три и шесть раундов. Это пределы ресурсов, а не доказанное ранжирование моделей по интеллекту или скорости. Цикл ограничен также общим числом инструментов на запрос. После каждого применённого пакета следующий раунд получает фактический результат и свежий контекст сцены.

От этой настройки отделены маршруты игрового pipeline. В системе выделены три текстовые задачи: Terrain, Dialogue и Planning. Для каждой OrchestratorProfile содержит отдельную ссылку на ModelProfile. Метод Resolve проверяет наличие маршрута и возвращает явно назначенный профиль. Такая организация допускает разные модели и endpoints без изменения компонента NPC.

Terrain требует короткой интерпретации параметров. Dialogue формирует русскоязычную речь с учётом знаний и личности. Planning выбирает высокоуровневое действие на основе компактного состояния мира. Embeddings выделены в отдельный IEmbeddingProvider, поскольку их результат имеет другой тип и не должен обрабатываться как текстовый completion.

В смешанной демонстрационной конфигурации диалог выполняется бесплатной облачной моделью, а Terrain и Planning — локально. Причина связана с ограничением частоты анонимного API: отправлять в облако все вспомогательные задачи означало бы занимать редкие доступные интервалы запросов. Детерминированная проверка остаётся обычным C#-кодом и не требует ещё одной модели.

Такой router не является системой совместного обсуждения нескольких агентов. Он не осуществляет голосование или автоматическую оценку «умности» моделей. Его назначение — разделить задачи и сделать выбранный маршрут наблюдаемым. В текущей версии отказ провайдера не вызывает скрытого перехода на fixture или mock, поскольку это исказило бы демонстрацию и измерения.

Кэш экземпляров провайдеров внутри ModelRouter уменьшает число создаваемых HTTP-клиентов. Освобождение pipeline закрывает принадлежащие ему сетевые ресурсы. Перед сменой профиля демонстрационный интерфейс освобождает прежние services; смена модели становится явным действием разработчика или пользователя demo.

## 2.4 Абстракция провайдеров и сетевой контракт

Интерфейс ILLMProvider содержит CompleteAsync, HealthAsync и Dispose. CompletionRequest включает сообщения и JSON Schema ожидаемого объекта. CompletionResult содержит текст, фактический provider/model, задержку и доступные счётчики токенов. При отсутствии метрики она не восстанавливается по предположению.

LocalProvider использует native API Ollama. Схема передаётся в format, streaming выключен, а для выбранной локальной модели отключается дополнительный thinking-вывод. Native API позволяет получить prompt_eval_count, eval_count и eval_duration. Эти данные нужны для измерения локальной скорости вывода и не подменяются скоростью сети [17].

OpenAICompatibleProvider реализует общий формат chat completions с отдельными особенностями Groq и Pollinations. Совместимость означает поддержку проверенного подмножества полей. Она не гарантирует идентичность всех API: путь получения моделей, имя параметра ограничения токенов и поддержка строгой схемы могут отличаться [21, 22].

ModelProfile хранит endpoint, model ID, timeout, число повторов, temperature и лимит токенов. Если нужен ключ, сериализуется только имя переменной окружения. Конструктор проверяет, что адрес использует HTTPS или локальный loopback HTTP, не содержит credentials, query и fragment. Автоматические redirects отключены, чтобы заголовок Authorization не передавался неожиданному хосту.

JsonTransport ограничивает объём ответа двумя мебибайтами. Чтение тела остаётся под действием timeout и cancellation token; иначе timeout только на получение заголовков не защитил бы от зависшего потока. Ошибки 400 и недоступная модель не должны повторяться как временная проблема. Для 429, 408 и серверных ошибок предусмотрены ограниченные повторы. Для HTTP 402 временным пределом считается только код FREE_LIMIT: без Retry-After ожидаются 46 секунд; платёжный механизм не вызывается.

Важна разница между транспортным успехом и прикладным. HTTP 200 подтверждает получение тела, но не валидность NpcDecision. EditorPlan и NpcDecision проверяются ещё раз после десериализации соответствующими прикладными валидаторами. При JSON Object Mode схема дополнительно описывается в system-сообщении, поскольку сам этот режим гарантирует только синтаксическую форму JSON, а не точные поля.

## 2.5 Архитектура знаний и памяти

KnowledgeBase представляет редактируемый ассет со списком KnowledgeDocument. Документ имеет идентификатор, Scope, заголовок, текст и MemoryKind. Chunk сохраняет идентификатор исходного документа, смещение, область видимости, текст и вектор. Такая структура обеспечивает связь найденного результата с авторским источником.

TextChunker использует окна по 500 символов с перекрытием 80 символов. Размер задан в символах, а не в токенах; это осознанное упрощение для короткого русского лора. Идентификатор chunk вычисляется через SHA-256 от scope, документа, смещения и содержимого. Повторная индексация одинакового текста даёт тот же идентификатор, а перенос текста другому персонажу меняет его.

Для получения векторов используется EmbeddingGemma. Модель предназначена для многоязычных текстовых представлений; в проверенном локальном запуске получены векторы размерности 768 [19]. Запрос и документ имеют разные префиксы, что соответствует поисковому назначению embedding-модели [20]. Документы не интерпретируются как инструкции разработчика.

Для векторов a и b косинусное сходство определяется как отношение скалярного произведения к произведению норм. Значение зависит от направления векторов, а не от их абсолютной длины. Нулевые векторы обрабатываются отдельно, а несовместимая размерность и нечисловые значения отклоняются. Изменение embedding-модели требует перестроения индекса, поскольку сравнение в разных пространствах не имеет корректной интерпретации.

InMemoryVectorStore сначала ограничивает множество документов по Scope и MemoryKind, затем вычисляет сходство и выбирает top k. При равных score порядок стабилизируется идентификатором, чтобы исключить случайную перестановку результатов. Для N фрагментов размерности d стоимость одного полного поиска составляет O(Nd). Для демонстрационного корпуса эта сложность приемлема и проще для проверки, чем приближённый индекс.

RagIndex различает статические знания, эпизодические события и разговорную память. Для основной базы применяется настраиваемый top k, дополнительно извлекаются до двух эпизодических и двух разговорных фрагментов. При сборке контекста общий текст retrieved ограничивается 4000 символами. Это ограничение не является точным токеновым budget, поэтому максимальный размер всей prompt также зависит от описания личности и состояния мира.

Память ограничена 32 последними документами текущего сеанса. При превышении пределa старый документ и соответствующие ему chunks удаляются. Индекс не является системой постоянного сохранения игры: завершение процесса уничтожает его содержимое. Статическая KnowledgeBase остаётся ассетом и может быть проиндексирована повторно.

Постоянная история редакторского чата хранится отдельно от памяти персонажа. ChatHistoryStore сохраняет беседы и настройки в UserSettings проекта, а в очередной запрос включается ограниченная часть последних сообщений и результатов инструментов. Эта история помогает продолжать авторинг; она не индексируется автоматически как личное знание каждого NPC. Такое разделение предотвращает смешение разработческой переписки и игрового лора.

Перестроение статического индекса выполняется через временное хранилище. Новый backend становится активным после успешной обработки всех документов и проверки cancellation token. Это защищает предыдущий индекс от частичной замены при отмене. Ошибка индексации памяти после уже исполненного действия фиксируется отдельно и не должна превращать произошедшую передачу предмета в фиктивный откат.

Для поиска используется косинусная мера

[[MATH_COSINE]]

Здесь q — вектор запроса, d — вектор фрагмента, D = 768 — размерность представления проверенной модели. После фильтрации результат представляет упорядоченный список пар «фрагмент, score». Значение score не является вероятностью истинности текста. Даже высокий показатель означает близость представлений, поэтому предметная достоверность должна оцениваться отдельно по ответу и источнику.

При N фрагментах и d координатах память самих векторов имеет порядок 4Nd байт для float32, без учёта строк и объектов среды выполнения. Например, для 1000 фрагментов размерности 768 числовая часть занимает примерно 3,07 МБ. Это расчёт объёма представления, а не измерение полного потребления процесса. Такая оценка объясняет выбор простого точного поиска для небольшого корпуса и необходимость другого backend при существенно большем N.

Граница Scope относится к доступу к данным, а не к качеству ранжирования. Если запрос совпадает со служебным паролем другого персонажа, этот документ всё равно исключается до вычисления сходства. Проверка scope входит как в формирование индекса NPC, так и в контракт поиска. Двойное ограничение защищает от случайного смешивания документов при дальнейшем расширении хранилища.

## 2.6 Спецификация и генерация Terrain

TerrainSpec содержит seed, физические размеры, разрешение, параметры fBm, силу горного края, глубину долины, уровень воды, южное понижение и число проходов сглаживания. Текущая версия использует один тип шума и не предоставляет произвольные карты биомов или гидравлическую эрозию. Выбор ограниченного набора параметров уменьшает неоднозначность JSON-контракта.

| Поле | Смысл | Допустимая область |
|---|---|---|
| seed | Начальное условие шума | Целое число |
| width и length | Размер поверхности | От 32 до 2048 единиц Unity |
| height | Масштаб высоты | От 4 до 512 |
| resolution | Размер регулярной сетки | 33, 65, 129, 257 или 513 |
| octaves | Число шумовых октав | От 1 до 8 |
| mountainStrength | Выраженность горного края | От 0 до 1 |
| valleyDepth | Центральное понижение | От 0 до 0,8 |
| waterLevel | Нормированная высота воды | От 0 до 0,8 |
| smoothingPasses | Проходы сглаживания | От 0 до 8 |

Валидация проверяет числовые типы и диапазоны до выделения карты. Например, дробное resolution не округляется в допустимое целое, а считается нарушением контракта. Это важно, поскольку автоматическое преобразование типов могло бы скрыть ошибку модели и затруднить сопоставление запроса с фактическим результатом.

Шумовая функция использует целочисленный hash координат и seed, сглаженную интерполяцию соседних значений и ограниченное число октав. После базового fBm к поверхности добавляется радиальный горный край и вычитается центральная долина. Множитель southSlope понижает южную часть края. Результат нормируется в диапазон, допустимый для TerrainData.

Сглаживание выполняется синхронно: каждый проход читает предыдущую карту и пишет новую. Это исключает зависимость результата от порядка обхода обновляемых ячеек. Используемый фильтр не моделирует перенос воды или осадка, поэтому в документации он не называется физической эрозией.

Для чата инструмент create_world принимает частичную спецификацию, дополняет отсутствующие значения установленными значениями по умолчанию и передаёт результат тому же TerrainGenerator. WorldComposer добавляет слои поверхности, воду, растительность, дома, освещение и камеру. Пресеты alpine, forest и desert задают параметры и цветовую палитру, а не обещают физически достоверные биомы. Распределение декора использует seed, высоту Terrain, ограничения уклона, воды и расстояния между объектами. Если запрошенное число объектов невозможно разместить в пределах попыток, операция завершается ошибкой с откатом, а не объявляет неполный набор успешным.

Инструмент update_world изменяет только собственный мир или Terrain: копирует TerrainData в новый ассет, применяет частичные параметры и обновляет высоты, слои, collider и воду. Помеченные объекты окружения привязываются к новой поверхности. Прежний TerrainData не изменяется, что защищает другие ссылки на него. Отдельный Regenerate расширенного инспектора сохраняет механизм Undo для GeneratedTerrain [25]. В обоих путях отмена сцены после успешной генерации может оставлять новые ассеты в Project; файловый результат не следует считать полностью отменённым только по исчезновению GameObject.

Расчёт нормированного шума при O октавах имеет вид

[[MATH_FBM]]

Амплитуда начинается с единицы и умножается на persistence после каждой октавы, частота начинается со scale и умножается на lacunarity. Seed октавы равен seed + 1013o с переполнением в установленной целочисленной арифметике. Такая конкретизация нужна для воспроизведения алгоритма, поскольку одно название fBm не определяет реализацию шума.

Финальная высота до ограничения диапазона получается суммой базового уровня 0,20, шумового вклада 0,24F, горного края с южным коэффициентом и отрицательного вклада долины. После этого применяется Clamp01. WaterLevel не изменяет поле высот: он определяет высоту дополнительной визуальной плоскости. Поэтому изменение уровня воды и изменение формы дна являются разными операциями.

Для внутренних ячеек проход сглаживания p выражается формулой

[[MATH_SMOOTH]]

Здесь avg₄ обозначает среднее четырёх соседей. Край массива в проходе сохраняется. Алгоритм является локальным усреднением и не моделирует перенос массы или потоки воды. При описании результатов термин «эрозия» для этой операции не используется.

## 2.7 Контракты редакторского агента и игровых действий

Редакторский план EditorPlan содержит reply, complete и массив actions. Поле reply предназначено для объяснения, complete обозначает завершение задачи на текущем шаге. Команда EditorCommand имеет tool, name, target и args. Перечень имён инструментов закрыт; типы, диапазоны и допустимые ключи args проверяются отдельно для каждой операции. Лишние поля и повторённые JSON-свойства отклоняются. План с пустым actions допускает объяснение без изменения сцены.

| Группа | Инструменты | Изменяемый или читаемый результат |
|---|---|---|
| Окружение | create_world, update_world, scatter_objects | Terrain, вода и собственный декор |
| Объекты сцены | create_object, set_transform, set_material, delete_object | Компоненты и параметры явно указанных целей |
| Свет и обзор | set_lighting, create_camera | Источники света и камеры |
| Персонажи | create_npc, update_npc, attach_behavior | Runtime-компоненты, знания и встроенное поведение |
| Наблюдение | inspect_object, search_project, read_script | Сведения без изменения сцены |
| Сохранение | save_scene | Копия сцены по разрешённому уникальному пути |

Контекст ограничен и содержит идентификаторы и параметры не более 80 объектов, выделение, настройки Terrain и NPC, существующие собственные группы и доступные инструменты. Цель вида id:число относится к объекту текущего сеанса Editor; это не постоянный идентификатор после перезапуска проекта. Ссылка @Name разрешает обратиться к более раннему созданию того же плана. Валидатор строит виртуальный набор целей, поэтому корректная последовательность «создать — настроить» допускается без предварительной мутации. Ссылка на будущее или уже удалённое создание отклоняется.

До исполнения проверяется весь пакет. В один план допускается не более 24 команд, в одно пользовательское обращение — не более 48 вызовов инструментов. Распределение ограничено 300 размещениями; полный бюджет учитывает дочерние GameObject и составляет 600 новых объектов на пакет и 2000 собственных объектов активной сцены. Дерево, дом и персонаж поэтому учитываются по составу, а не как одна строка в плане. Числовые параметры должны быть конечными; пути не допускают выхода из разрешённого каталога.

При изменении сцены создаётся одна группа Undo. Исполнитель ведёт список вновь созданных ассетов и возвращает идентификаторы объектов и прочитанные параметры. При ошибке исполнения отменяется группа сцены и удаляются только файлы, зарегистрированные текущим пакетом; ошибка очистки также включается в результат. Операции inspect_object, search_project и read_script не создают Undo-группу. Успешные несколько раундов образуют несколько завершённых пакетов, поэтому отмена последнего пакета не равна откату всей беседы. Остановка ожидания после уже завершённого раунда не отменяет этот раунд автоматически.

Изменение материала создаёт отдельный Material, сохраняя чужой sharedMaterial. Новые ассеты записываются в уникальный подкаталог Assets/WorldWeaverGenerated/Assistant. Сохранение сцены выполняется только явной последней командой save_scene по уникальному пути внутри Assets/WorldWeaverGenerated; существующие файлы и список сборки не перезаписываются. Успешный Undo относится к объектам сцены: оставшиеся после него ассеты требуют отдельного учёта. Таким образом, откат ошибочного пакета и отмена ранее успешного действия имеют различную файловую семантику.

Генерация C# вынесена в отдельный контракт. draft_script предлагает полный исходник MonoBehaviour, который всегда показывается для просмотра перед импортом, даже при включённом автоматическом применении обычных инструментов. Допускается создание или исправление только собственных помеченных файлов Assets/WorldWeaverGenerated/Scripts. После импорта фиксируются реальные события компилятора Unity. Только отдельная команда attach_script может подключить уже скомпилированный компонент к явно указанному объекту через Undo. План кода не смешивается с пакетом обычных изменений сцены, поскольку компиляция и перезагрузка домена имеют иной жизненный цикл.

Предварительный фильтр ограничивает имена, размер исходника, Editor-only конструкции и известные шаблоны credentials. Он не является формальным анализатором безопасности. Компилятор проверяет синтаксис, типы и ссылки, но не доказывает правильность игрового поведения и не создаёт sandbox. Сгенерированный компонент после просмотра исполняется с правами процесса Unity. Поэтому этот путь требует содержательной проверки кода; его нельзя описывать как безопасное исполнение произвольной программы. Каждый импорт получает отдельную постоянную запись журнала, связанную с беседой и сообщением: версии собственных файлов до и после импорта, контрольные суммы и исход компиляции. Второй импорт B сохраняет запись первого импорта A. Кнопка возврата кода у соответствующего сообщения восстанавливает файлы только при совпадении текущего содержимого с версией после этого импорта. Для последовательных изменений одного файла сначала возвращается B, затем A; попытка возврата A поверх B отклоняется. Такая проверка также сохраняет последующие ручные правки пользователя. Возврат файлов проходит повторную компиляцию и учитывается отдельно от обычного Undo сцены.

Игровой контракт отделён от редакторского. Ответ NPC имеет два обязательных поля: speech и actions. Каждая команда содержит type, target, item и amount. Даже для действия без предмета поля сохраняются: item и target при необходимости равны пустой строке, amount равен нулю. Единый DTO упрощает совместимость разных JSON-режимов.

NpcDecision.Parse отклоняет неизвестные и дублирующиеся поля, неправильные типы, чрезмерно длинные строки и массивы более четырёх действий. Структурная схема полезна для генерации, но не заменяет прикладные проверки. JSON Schema задаёт форму объекта, а право на изменение инвентаря определяется текущим миром [26].

ActionDispatcher хранит реестр IGameAction. Для встроенных операций используются TransferAction и WorldAction. Добавление нового обработчика через Register не требует изменения router. Пользовательский обработчик обязан выполнять Validate без изменения сцены; нарушение этого контракта делает общую предварительную проверку бессмысленной.

Перед исполнением решения dispatcher формирует словарь явно известных NPC сущностей. Неизвестный target и повторяющийся entity ID приводят к отказу. Для передачи предметов создаётся проекция каждого затронутого инвентаря. Она резервирует количество и вместимость до реального изменения объектов. Так два действия по шесть кристаллов не могут оба пройти при исходном остатке десять.

Количество передаваемых предметов ограничивается не только остатком, но и общим MaxTransferPerDecision. Проверяются дальность взаимодействия и разрешение TakeItem. Текстовое ограничение «не отдавай много» не считается заменой этих полей. Для перемещения проверяется наличие агента на NavMesh и полный путь к достижимой точке.

После успешного предконтроля действия выполняются последовательно без await в главном потоке. Это предотвращает изменение состояния между проверкой и записью из-за другого продолжения async-метода. Для встроенных инвентарных операций такой порядок обеспечивает согласованную передачу. Полный rollback произвольных пользовательских действий во внешних системах текущий интерфейс не гарантирует.

## 2.9 Выбор локальной среды и ограничения развёртывания

Для локального inference рассмотрены Ollama, LM Studio и llama.cpp. Все три подхода позволяют организовать локальное исполнение, однако отличаются управлением моделями и API [17, 33, 34]. На машине уже был установлен Ollama, поэтому его использование уменьшило объём изменений среды и позволило проверить реальные запросы через один локальный daemon.

Apple M4 имеет объединённую память, которую одновременно используют Unity, операционная система и inference. Выбор моделей для базовой runtime-конфигурации версии 1.0 учитывал это ограничение. Установка модели на 120 миллиардов параметров не соответствует доступным 16 ГБ. Поэтому для коротких запросов Terrain и QA выбрана небольшая Qwen3.5 2B и отдельная embedding-модель; для итогового Dialogue и Planning дополнительно используется квантованная qwen2.5-coder 7,6B. Выбор основан на возможности совместного запуска, а не на попытке воспроизвести cloud-модель на любом оборудовании [18].

Бесплатный Pollinations API не требует ключа, но ограничивает частоту и не гарантирует доступность [23]. Это делает его пригодным для демонстрации и сравнительного опыта при соблюдении интервалов, но не позволяет обещать фиксированную задержку в коммерческой игре. Локальная конфигурация остаётся обязательным воспроизводимым вариантом.

Рисунок показывает физическое развёртывание редакции 1.1. Unity содержит редакторский чат и runtime-компоненты; Ollama выполняется отдельным локальным процессом и вызывается по loopback HTTP. Начальная модель чата — Qwen3.5 9B, остальные установленные текстовые модели доступны для выбора, а EmbeddingGemma формирует векторы для retrieval. Перечисление моделей не предполагает одновременную загрузку всех весов.

История бесед и постоянный журнал импортов C# с предыдущими версиями файлов хранятся в UserSettings проекта. Созданные Terrain, материалы, сцены, знания NPC и просмотренные скрипты записываются в Assets/WorldWeaverGenerated. Необязательный маршрут Pollinations Classic использует HTTPS: текущий серверный предел составляет один ответ за 45 с на IP, клиентский интервал — 46 с, max_tokens — 1500 [39]. Исходное QA-исследование версии 1.0 сохраняет собственные модели и интервал 31 с в протоколе четвёртой главы; эти исторические условия не обозначают текущую квоту сервиса.

![Развёртывание редакторских, игровых и модельных компонентов WorldWeaver 1.1](docs/uml/deployment.png)

Проектная архитектура задаёт наблюдаемую границу ответственности: редакторская модель предлагает EditorPlan, исполнитель возвращает фактическое состояние и результат; runtime-retrieval выбирает доступные персонажу факты, а ActionDispatcher проверяет игровые последствия. Отдельный путь просмотренного C# расширяет возможности продукта и требует отличающихся правил проверки и восстановления. Следующая глава описывает, как эти границы реализованы в программных компонентах.
