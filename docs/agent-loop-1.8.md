# Проверяемое поведение агента в кандидате 1.8

Статус: кандидат для испытаний; версия ещё не опубликована и не установлена в пользовательский проект. Прохождение отдельных проверок ниже не является подтверждением выполнения полного игрового запроса.

## Контракт результата

Исходный запрос пользователя хранится отдельно от предложенного моделью плана. При проверке этапа `OriginalRequest` всегда содержит запрос пользователя, а `TentativeStage` — предполагаемый способ работы. План не добавляет обязательные имена классов, число файлов или разрешения.

История нативных инструментов содержит ограниченную последовательность реальных вызовов и ответов, включая отклонённые вызовы с явным `executed:false`. Пустой ответ может вызвать переход к JSON-контракту с теми же проверками аргументов. История инструментов передаётся как факты, внутреннее reasoning-состояние не превращается в обычный текст. Ошибка выбора недоступного на текущем этапе инструмента не считается неисправностью native-протокола и не переключает подключение в другой режим. В узкой фазе планирования сообщение восстановления предлагает сначала выполнить доступный `plan_task`, а не вызывать скрытый `discover_tools`.

У успешного результата может быть `ChangesApplied:false`: например, требуемый компонент уже существует или значение поля не изменилось. Такая операция не сбрасывает счётчик отсутствия прогресса и не является доказательством нового изменения.

## Произвольная проверка в Play Mode

`run_runtime_probe` компилирует C# iterator с параметром `RuntimeProbeContext probe`. Он может измерять созданную механику, подавать виртуальные клавиши/мышь или UI-события, пропускать реальные кадры и записывать вычисленные утверждения. Инструмент не содержит готовой складской, планетарной или другой игровой реализации.

- `probe.Record(name, measuredValue)` сохраняет ограниченные измеренные данные.
- `probe.Check(condition, name, observedValue)` сохраняет результат условия и его наблюдаемое значение.
- При включённом Input System проба устанавливает временные устройства до запуска iterator. Они доступны через `probe.Keyboard` / `probe.Mouse` и обычные `Keyboard.current` / `Mouse.current`, включая редактор без физических устройств. После проверки устройства удаляются, прежние текущие устройства и маршрутизация ввода восстанавливаются.
- Допускается `yield return null`. Ожидание строится по наблюдаемому времени игры. Проба без утверждений, ложное утверждение, исключение, отмена и превышение времени не дают успешного результата.
- Результат становится окончательным после выхода из Play Mode. Исходная Editor-сцена восстанавливается; временные перестановки при проверке не считаются реализацией запроса.

Проба требует разрешения на автономный Editor C#. Она выполняет доверенный код с правами Unity, как `execute_editor_code`; это не песочница. Предел времени контролирует код, который отдаёт управление через `yield`, и не может прервать блокирующий синхронный C#. Проверочные snippets не должны выполнять файловые, сетевые, платёжные операции, сохранять сцену или менять настройки редактора.

Неудачный `job_result` остаётся в доступном модели журнале наблюдений вместе с измерениями. После изменения исходников устаревшая runtime-проба помечается как требующая нового измерения; её исходник можно получить по сохранённому шагу. Повторное чтение и импорт неизменившегося скрипта не наращивают служебные комментарии и не считаются исправлением.

Утверждения пишет сама модель: они подтверждают только реально проверенные свойства. Независимая приёмка готового артефакта остаётся отдельным этапом.

## Сохранность проекта и восстановление

Пустые, оборванные и не прошедшие проверку ответы не применяются частично. После двух последовательных ошибок формы wire-ответа доступен JSON-контракт с тем же валидатором действий. Семантические ошибки, отсутствующая цель и вызов скрытого текущим этапом инструмента не подтверждают неисправность протокола. Принятый корректный шаг сбрасывает счётчики последовательных ошибок формы; отдельная защита от отсутствия прогресса продолжает учитывать бесполезные чтения и операции без изменений. Все попытки остаются в журнале.

Редакторский C# и runtime-проба получают алиасы `Object = UnityEngine.Object` и `Random = UnityEngine.Random`; явно заданный в коде алиас имеет приоритет. Это устраняет неоднозначность стандартных Unity API при автоматически подключённом `System`.

Контроль checkpoint остаётся строгим: ручные изменения сцены и материалов блокируют автоматическое продолжение. Перед фиксацией собственных изменений новые/изменённые материалы поддерживаемого URP-шейдера инициализируются штатным ShaderGUI. Чужие материалы не сохраняются; изменение одного материала считается реальным изменением. Это устраняет ложный конфликт от штатной ленивой инициализации URP при входе в Play Mode.

Для относительных изменений начальный снимок содержит также статическую геометрию. Проверяющий получает исходный запрос, исходные значения и текущие измерения, а не только предложенный моделью этап. Количество классов и выбранные моделью имена не становятся обязательными требованиями пользователя.

Checkpoint сохраняют одинаковое содержимое по SHA-256 один раз в общем пуле с небольшими ссылками каждого журнала. Старый формат читается для совместимости; восстановление проверяет хеши. Пул ограничен 2 ГиБ, отдельный снимок — 300 МиБ. Сборщик удаляет только данные без ссылок, сохраняя действующие точки восстановления. Ресурсы QA и проведённая очистка описаны в [qa-resource-policy.md](qa-resource-policy.md).

## Границы вывода

Успех сохранённой сцены при независимой проверке не превращает ошибочный ответ контроллера в успешный. Написанная моделью проба не является независимым аудитом. Проверка этих задач не доказывает выполнение произвольного запроса, превосходство над Unity AI или замену разработчика. Доступность бесплатного облака, скорость ответа и качество планирования зависят от провайдера и модели; они не гарантируются пакетом.
