## Текст основного доклада

### Слайд 1. Титульный слайд

Уважаемые члены государственной экзаменационной комиссии! Представляю выпускную квалификационную работу на тему «Разработка интеллектуального инструментария для автоматизированного создания динамических игровых миров». Практический результат работы — подключаемый пакет WorldWeaver для Unity, который объединяет создание рельефа, индивидуальные знания персонажей и исполнение игровых действий после проверки.

### Слайд 2. Проблема согласованного игрового мира

При создании мира разработчик решает несколько связанных задач: формирует окружение, описывает персонажей и задаёт последствия общения с ними. Языковая модель помогает интерпретировать свободный текст, но её реплика ещё не подтверждает изменение игры. Например, обещание отдать кристалл должно согласоваться с наличием предмета, правами персонажа и фактическим изменением обоих инвентарей. Эта граница стала основой архитектуры.

### Слайд 3. Цель и задачи работы

Цель — разработать и экспериментально оценить переносимый инструментарий Unity для генерации рельефа и контекстно-зависимых NPC. Для этого были сформулированы требования, спроектированы модельные маршруты и контракты, реализованы генератор Terrain, индивидуальный RAG и система действий. Проверка разделена на программные инварианты, реальные обращения к моделям и сравнительный опыт с вопросами к базе знаний.

### Слайд 4. План решения

Работа выполнена последовательно: анализ аналогов, техническое задание, проектирование, реализация и испытания. Для каждого этапа подготовлен проверяемый результат: архитектурные диаграммы, исходный код, устанавливаемый пакет, демонстрационная сцена и протоколы. Такое разделение позволяет сопоставить заявленное требование с конкретной реализацией и способом проверки.

### Слайд 5. Сопоставление с существующими решениями

Изучены Unity AI, Convai, Inworld, средства Procedural Worlds, LLMUnity и общие RAG-фреймворки. Готовые решения уже предоставляют существенную часть рассматриваемых возможностей. Вклад WorldWeaver состоит в их инженерном объединении: типизированное описание Terrain, индивидуальная область знаний, раздельные маршруты моделей и детерминированная проверка последствий внутри UPM-пакета. Сравнение выполнено по первичным источникам; одинаковые нагрузочные испытания коммерческих продуктов не проводились.

### Слайд 6. Основные требования

Инструментарий должен подключаться к проекту, предоставлять окно Editor, создавать рельеф по описанию и поддерживать настройку нескольких NPC. Для знаний предусмотрен импорт TXT, Markdown и JSON. Для действий заданы разрешённые цели, предел передачи предметов и проверка доступности пути. Требования также включают диагностику, отмену сетевого запроса и контролируемую обработку ошибок. Голос и импорт PDF в проверенную версию не входят.

### Слайд 7. Прецеденты использования

Диаграмма выделяет две основные роли. Разработчик настраивает модели, рельеф, персонажей и знания, затем исследует результат через журнал. Игрок общается с NPC и наблюдает игровые последствия. Отдельно предусмотрено автономное планирование по цели персонажа. Оно проходит тот же исполнительный контур и ограничивается собственным разрешённым набором действий.

### Слайд 8. Обработка реплики и автономной цели

Обработка начинается со сбора контекста и поиска знаний. Затем выбирается маршрут Dialogue или Planning и выполняется запрос к модели. Полученный JSON разбирается по строгому прикладному контракту. До изменения сцены проверяется весь пакет встроенных действий. При нарушении условий сохраняется причина отказа; после завершения решения фиксируются речь, события памяти и диагностический trace.

### Слайд 9. Диалог с передачей предмета

На диаграмме последовательности показан пример передачи кристалла. Pipeline сначала получает релевантные фрагменты, затем передаёт модели сообщения и схему ответа. Dispatcher проверяет цель, количество, остаток и вместимость. Изменение Inventory выполняется после успешной предварительной проверки. В память записывается результат исполненного действия. Поэтому речь, структурированное решение и фактическое состояние доступны для отдельного сопоставления.

### Слайд 10. Компоненты инструментария

Пакет разделён на Runtime и Editor. Окно редактора создаёт ассеты и настраивает профили. Во время игры IntelligentNPC обращается к NpcPipeline, который соединяет retrieval, модельный router и dispatcher. Для Terrain модель выбирает параметры спецификации, а отдельный C#-генератор вычисляет высоты. Сетевой провайдер непосредственно не изменяет объекты Unity.

### Слайд 11. Контракты и точки расширения

Интерфейсы выделены для текстовой модели, embeddings, векторного хранилища и игрового действия. Это позволяет заменять отдельные реализации. Для пользовательского действия предусмотрены Validate и Execute. Validate обязан работать без изменения сцены. Общая предварительная проверка встроенных операций не означает универсальный rollback произвольного внешнего действия — такой протокол расширение должно проектировать отдельно.

### Слайд 12. Потоки данных и граница доверия

На этой схеме важны границы доступа. Документы сначала ограничиваются идентификатором персонажа и только затем ранжируются по близости. Высокое сходство не открывает NPC чужую базу знаний. Внешний сервис получает ограниченный текстовый контекст и возвращает структурированное предложение. Допустимость изменения Inventory или маршрута движения определяет код игры. Однако смысловая правильность любой реплики этим автоматически не гарантируется.

### Слайд 13. Развёртывание и модельные маршруты

Основная проверенная среда — Unity 6.3 LTS на Apple M4 с шестнадцатью гигабайтами памяти. Локальный inference выполняется через Ollama, embeddings — через EmbeddingGemma. В сравнительном QA-эксперименте используется Qwen3.5 2B. В финальной игровой демонстрации Dialogue и Planning используют Qwen2.5-Coder 7.6B. Для бесплатного облачного диалога проверен Pollinations с фактической GPT-OSS 20B. Результаты этих разных задач и моделей учитываются раздельно.

### Слайд 14. Генерация Terrain в Unity

Здесь представлены реальные изображения редактора. Описание преобразуется в редактируемый TerrainSpec с проверяемыми диапазонами. Генератор использует value noise, сумму октав, горный край, долину, направленный уклон и сглаживание. Одинаковая спецификация и seed воспроизводят массив высот в проверенной среде. Реализованы вода, простая высотная раскраска и Undo собственного Terrain. Выразительность ограничена этим семейством форм; новый алгоритм шума не заявляется.

### Слайд 15. Программные испытания

Текущий набор содержит 56 пройденных EditMode-проверок и два детерминированных PlayMode-теста. Проверены строгий JSON, изоляция знаний, лимиты инвентаря, сетевые ошибки, движение и остановка. Добавлена регрессия отмены после уже исполненного действия. Отдельная установка архива в чистый проект подтвердила компиляцию, сохранность предыдущей demo и списка сборки, а также обновление раскраски при повторной генерации. Реальные модельные испытания выделены отдельно от этих проверок.

### Слайд 16. Реальный сценарий торговца

В двух финальных интеграционных прогонах игрок получил один Crystal, а NPC переместился к House. Локальному диалогу потребовались два хода, облачному — один; planning в обоих случаях был локальным. Сохранены исходные реплики, решения и изменения состояния. При этом локальная речь частично расходилась с выполненной передачей. Дополнительный GUI-повтор передал предмет, но вернул пустой actions и нулевое перемещение. Значит, завершение двух тестовых сценариев подтверждено, а устойчивость свободного поведения остаётся ограниченной.

### Слайд 17. Совпадение с известным ответом и завершение доклада

Эксперимент включает тридцать вопросов в трёх конфигурациях: всего девяносто запросов, восемьдесят девять полученных ответов и одну ошибку HTTP 400. Для одной локальной модели добавление RAG повысило совпадение известного факта в исходной речи с 2 до 20 случаев из 30; облачная конфигурация дала 29 из 30. После проверки всего решения ожидаемый факт дошёл до игрока в 16 случаях из 30 у обеих RAG-конфигураций. Поэтому качество retrieval, исходной речи и целого pipeline различаются. Метрика не является процентом отсутствия галлюцинаций. Протокол заморожен тегом experiment-2026-10-30 и не выдан за повтор после последующих исправлений.

## Вероятные вопросы комиссии

### 1. В чём ваш собственный вклад, если RAG и процедурная генерация уже существуют?

Вклад — проектирование и реализация общего Unity-контура: TerrainSpec, индивидуальная область знаний, явная маршрутизация задач, строгий разбор NpcDecision, предварительная проверка действий, Editor и воспроизводимые проверки. Использованные методы шума, retrieval и NavMesh известны; их авторство я себе не приписываю.

### 2. Чем решение отличается от LLMUnity, Convai или Inworld?

Это ограниченный исследовательский инструментарий с общим процессом настройки Terrain и NPC, разными HTTP-провайдерами и явно проверяемым исполнительным слоем. Готовые SDK уже решают многие задачи персонажей. Превосходство по художественности, скорости или полноте функций экспериментом не доказано.

### 3. Почему модель не генерирует C# и не управляет Transform каждый кадр?

Структурированные параметры и высокоуровневые действия дают конечный проверяемый контракт. Высоты вычисляет C#, а движение исполняет NavMeshAgent. Это сохраняет правила игры и позволяет независимо тестировать исполнитель. Произвольный код из ответа модели не выполняется.

### 4. Что в работе означает «динамический игровой мир»?

После авторинга окружения NPC отвечает с учётом контекста и памяти сеанса, передаёт предметы и выбирает высокоуровневое поведение во время игры. Создание Terrain проверено прежде всего как операция Editor. Непрерывная генерация бесконечного мира, произвольные биомы и автоматическая навигация по любому Terrain не реализованы.

### 5. Почему выбраны разные локальные модели для QA и финальной demo?

QA фиксирует влияние RAG при одной Qwen3.5 2B, чтобы не менять модель между двумя локальными условиями. Для интерактивной demo позднее выбрана более крупная Qwen2.5-Coder 7.6B. Её качество нельзя выводить из QA-чисел 2B; соответствующие протоколы и задачи разделены.

### 6. Если правильный документ найден в 30 случаях из 30, почему ответ бывает неверным?

Hit@3 показывает присутствие размеченного источника среди трёх фрагментов. Модель может неправильно использовать этот текст, добавить противоречие или выбрать недопустимое действие. Поэтому retrieval, совпадение исходного факта и доставленный пользователю результат измеряются отдельно.

### 7. Можно ли назвать 29/30 точностью или отсутствием галлюцинаций?

Точная формулировка — совпадение допустимого варианта известного факта в исходной speech на заданном корпусе. Проверка не оценивает каждое дополнительное утверждение. Число 29/30 включает HTTP-ошибку в знаменателе и не доказывает отсутствие галлюцинаций либо корректность 96,7% произвольных игровых ответов.

### 8. Почему после проверки игрок получил правильный факт только в 16 случаях из 30?

Часть ответов содержала подходящий факт, но пакет действий нарушал действовавший контракт, например Talk с target Player вместо пустого target. Были также попытки движения в Editor без активной NavMesh. Это выявило проблему согласования выхода модели и исполнительного контракта. Отклонённые ответы сохранены и не исключены из результата.

### 9. Почему эксперимент зафиксирован тегом, а не пересчитан после исправлений?

Тег experiment-2026-10-30 сохраняет версию, для которой получены исходные запросы и ответы. После опыта изменялись Planning/schema и исправлялись программные пути. Старые результаты нельзя объявлять новыми измерениями этих изменений. Для оценки улучшения QA нужен отдельный новый прогон с обозначением версии и тем же протоколом.

### 10. Что именно гарантирует проверка действий? Есть ли полная атомарность?

Перед выполнением встроенного пакета проверяются разрешения, известные цели, количество, общий бюджет и проекция инвентарей. Проверка и исполнение проходят последовательно в главном потоке без await между ними. Отклонённый встроенный пакет не меняет инвентарь. Произвольный пользовательский обработчик или внешняя система требуют собственного протокола commit и компенсации; универсальный rollback не гарантируется.

### 11. Что произойдёт при отмене запроса после уже переданного предмета?

Отмена до commit прекращает обработку без нового действия. Если решение уже исполнено, последующая отмена индексации памяти сохраняется как отдельная диагностическая ошибка; результат действия и речь возвращаются. Исполненный предметный перенос не объявляется фиктивно отменённым. Этот случай покрыт новым EditMode-тестом.

### 12. Почему не проверялась экономия труда разработчика или удобство для новичков?

Контролируемое исследование с участниками не проводилось. Проверены исполнимость операций, установка и программные свойства. Чтобы измерить трудоёмкость, нужны одинаковые задания, сравнимые участники, базовый способ решения и заранее заданный протокол. Процент экономии труда по текущим данным заявлять нельзя.

### 13. Подходит ли бесплатный API для игрового диалога в реальном времени?

В проверенном маршруте существенное ограничение — один текстовый запрос примерно за 30 секунд на IP; код выдерживает 31 секунду и учитывает повторы. Для демонстрации и сравнительного опыта этого достаточно. Для непрерывного коммерческого диалога фиксированная доступность и задержка не подтверждены. Полностью локальный режим позволяет выполнять inference без облачной квоты, но зависит от ресурсов компьютера.

### 14. Что доказывают 56 EditMode, два PlayMode и два реальных интеграционных теста?

Первые группы проверяют конкретные программные свойства и физическое исполнение в заданной сцене. Два реальных теста подтверждают два успешных сценария с настоящим inference. Они не дают оценки 100% устойчивости. Дополнительный локальный GUI-повтор завершил передачу, но выбрал бездействие и не выполнил критерий перемещения; это ограничение сохранено в работе.

### 15. Какие основные ограничения и следующий шаг?

Текущие пределы — тридцать известных вопросов к небольшому миру, отсутствие независимого корпуса и многократных повторов, неполное согласование речи с действием и нестабильное planning. Память ограничена 32 документами сеанса и не сохраняется между запусками. Дальнейшая оценка требует новых вопросов, неизвестных фактов и конфликтов, повторов поведения и пользовательского исследования; расширение продукта — отдельная работа после таких измерений.
